# Passkeys start Sessions through the session module

Users asked to sign in without typing a password. UM now lets a User register Passkeys (WebAuthn credentials) and start a Session with one.

Decisions:

- **One relying party for every System.** UM is configured with one RP ID (`WEBAUTHN_RP_ID`, intended `devper.app`) and the exact page origins allowed to run a Ceremony (`WEBAUTHN_RP_ORIGINS`). A Passkey therefore works on every front end served under that domain and on none outside it; `*.web.app` hosts keep password login only (`web.app` is a public suffix). Without `WEBAUTHN_RP_ID` the Passkey routes answer 404 and nothing else changes.
- **Passkeys add to the password, they do not replace it.** Registering one requires the current password, so a stolen access token alone cannot add a Passkey. Password changes and admin resets keep the User's Passkeys; deleting a User deletes them. A User lists and deletes their own Passkeys.
- **The session module still owns starting a Session (ADR-0009).** After the WebAuthn assertion verifies, `session.Manager.StartWithPasskey` applies the same checks as a password login — ACTIVE, the User's Client has the System, SUPER only in SM — and issues the Session. The login lockout counts wrong passwords and does not apply: a forged assertion is not a guess that gets closer. The public Passkey routes are rate limited per IP like `/auth/login`.
- **Discoverable credentials, user verification required.** Login does not need a username; the authenticator offers the User's Passkeys, and front ends may also offer them in the username field through the browser's autofill (conditional mediation, 2026-10-30). If the login page has a username typed, `POST /auth/passkey/login` carries it and the passkey's owner must be that User (401 `UM-401-006` "this passkey belongs to a different account"), so a passkey picked by mistake cannot sign in as somebody else. Registration requires a resident key and user verification. A sign-count that goes backwards (a cloned authenticator) refuses the login.
- **Ceremonies live in Redis.** A Ceremony is stored for five minutes and consumed with `GETDEL`, so each challenge is answered once. Credentials live in MongoDB (`passkeys`), keyed by credential ID.

Consequences: front ends that want Passkeys must be served under the RP ID and listed in `WEBAUTHN_RP_ORIGINS` — today `https://port.devper.app`, `https://um.devper.app`, `https://pharm.devper.app` (pharmacy-web), `https://pharm-pos.devper.app` (pharmacy-app-kmp) and `https://alert.devper.app`. um-web registers Passkeys; every listed front end can sign in with the same one. Services that proxy login (PortForMe) proxy the two login routes and keep binding their own System.
